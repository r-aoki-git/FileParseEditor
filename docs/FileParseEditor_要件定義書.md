## 1. 目的

`FileParserLib`を利用して、LFCファイルの読み込み・編集・保存を画面から行えるWPFアプリケーション`FileParseEditor`を作成する。
本課題では、ライブラリの機能を画面に載せること自体よりも、以下の点を重視する。

- ライブラリの公開APIだけを使って、利用者（アプリ）の立場から必要な機能を実現できるか
- 型が混在する複数値・警告／エラーといったLFCの特徴を、画面上でどう見せ、どう入力させるか
- 不正な入力や保存されていない変更に対して、利用者が意図せずデータを失わないようにすること
- 画面（View）と処理（ロジック）を分離し、画面を操作しなくてもロジックを検証できる構成にすること

---

## 2. 前提

### 2-1. 利用するライブラリ

`FileParserLib`の公開API（`LfcDocument`、`LfcValue`、`LfcDiagnostic`など）だけを使い、内部（`internal`）のクラスには依存しない。
ライブラリの主な仕様は`FileParserLib_要件定義書.md`（v7）と`FileParserLib_基本設計書_10-02.md`のとおりであり、本書ではアプリ側の要件だけを定める。

| ライブラリの機能 | アプリでの用途 |
|---|---|
| `Load` / `CreateEmpty` / `Save` | ファイルを開く／新規作成／保存 |
| `Sections` / `Keys` / `Get` | セクション一覧・キー一覧・値の表示 |
| `Set` / `AddSection` / `Remove` / `RemoveSection` | 値の追加・変更、セクションの追加、キー・セクションの削除 |
| `Diagnostics`、`LfcLoadOptions.ThrowOnError` | 読み込み時の警告・エラーの表示 |

### 2-2. 利用者

LFCファイルの記法を理解している開発者・設定担当者を想定する。LFCの記法を知らない利用者向けの入力補助（ウィザード等）は設けない。

## 3. 機能要件

| No | 機能 |
|----|------|
| 1 | LFCファイルを選択して開ける（ファイルを開くダイアログ、またはウィンドウへのドラッグ＆ドロップ） |
| 2 | 新規に空のLFCデータを作成できる |
| 3 | セクションの一覧を表示できる（グローバルセクションを含む） |
| 4 | 選択したセクションのキーと値の一覧を表示できる（値の型が分かるように表示する） |
| 5 | 既存のキーの値を変更できる（複数値・型の混在・値なしを含む） |
| 6 | 選択したセクションにキーを追加できる |
| 7 | キーを削除できる |
| 8 | セクションを追加できる |
| 9 | セクションを削除できる（所属する全キーごと削除。削除前に確認する） |
| 10 | 上書き保存できる |
| 11 | 名前を付けて保存できる（ファイルを保存するダイアログ） |
| 12 | 読み込み時の警告（Warning）・エラー（Error）を、行番号・内容とともに一覧表示できる |

| 18 | 保存したときのテキスト（保存イメージ）を、コメントを含めて読み取り専用で表示できる。編集するたびに更新する |

## 4. 要求確認事項（決定事項一覧）

上司の指示は「`FileParserLib`を使い、WPFで読み込み・保存・編集ができるアプリケーションを作成する」のみであるため、以下は本書で決めた内容である。**「要確認」の項目は、レビューで方針を確認する。**

| No | 項目 | 決定内容 | 状態 |
|----|------|------|------|
| 1 | 画面構成 | 1つのメインウィンドウで操作する（4-1） | 要確認 |
| 2 | 値の入力方法 | LFCの値の表記（例：`1,"tasiro",2`）で入力する（4-2） | 決定 |
| 3 | 入力した値に警告となる記述がある場合 | 解釈した結果を示して確認し、了承されたら確定する（4-2） | 決定 |
| 4 | エラーを含むファイルの扱い | エラーがあっても開けるようにし、保存前に警告する（4-3） | 決定 |
| 5 | 元に戻す（Undo） | 編集操作を元に戻せるようにする（4-4） | 決定 |
| 6 | コメントの扱い | 保存イメージ欄で確認できるようにする。キーごとの表示と編集はしない。保存時はライブラリの仕様どおり保持する（4-5） | 決定 |
| 7 | 名前の変更 | キー名・セクション名の変更機能は設けない（6章） | 決定 |
| 8 | 同時に開くファイル数 | 1つ（別のファイルを開くと置き換わる） | 決定 |
| 9 | 画面の言語 | 日本語 | 決定 |

### 4-1. 画面構成

メインウィンドウを次の領域で構成する。

| 領域 | 内容 |
|---|---|
| メニュー／ツールバー | 新規作成、開く、上書き保存、名前を付けて保存、終了、元に戻す、セクションの追加・削除、キーの追加・削除 |
| セクション一覧（左） | セクション名の一覧。グローバルセクションは「（グローバル）」などと表示して区別する |
| キー一覧（右） | 選択したセクションのキー・値・型の表。値の編集はここで行う |
| 保存イメージ | 保存したときのテキスト（コメントを含む）。読み取り専用（4-5） |
| 診断情報一覧（下） | 読み込み時の警告・エラーの重大度・行番号・メッセージ |
| ステータスバー | 開いているファイルのパス、セクション数・キー数など |

### 4-2. 値の入力方法

LFCの値は「型が混在する複数値」であるため、LFCファイルと同じ表記のテキストで入力する（例：`1,"tasiro",2`）。

検討した案と、採用した理由は次のとおり。

| 案 | 内容 | 長所 | 短所 | 結論 |
|---|---|---|---|---|
| A | LFCファイルと同じ表記のテキストで入力する。型はライブラリと同じ規則で判定する | ファイルと同じ見た目で、複数値もまとめて入力できる。型判定の規則がライブラリと一致する | LFCの記法を知らないと入力できない | **採用**（利用者はLFCの記法を理解している前提のため（2-2）） |
| B | 要素ごとに「型」と「値」を選んで入力する | 型を明示でき、記法を知らなくても入力できる | 複数値の入力・並べ替えの画面が複雑になる | 不採用 |

入力の規則は次のとおりとする。

- 値は、保存時と同じ表記（例：`1,2.0,true,"文字列"`）で表示し、同じ表記で入力する。型は別の列に表示する
- 入力した表記は、ライブラリの読み込みと同じ規則で解釈する（型判定、エスケープ、空の要素は値なし）
- 読み込みであれば Warning になる記述（クォートなしの文字列 `Auto`、未定義のエスケープ `\d` など）がある場合は、解釈した結果（例：「`Auto` は文字列として扱います」）を示して確認し、了承された場合だけ確定する。確定した値は、保存時に `"Auto"` のようにクォート付きで書き出される
- 読み込みであれば Error になる記述（閉じていない引用符、文字列の後の不正な記述など）がある場合は確定せず、エラーメッセージを表示して入力をやり直させる
- 1つの値の入力欄では改行とコメント（`#`）は扱わない。文字列に改行を含める場合は `\n` と書く

### 4-3. エラーを含むファイルの扱い

ライブラリは、エラー（重複キー、セクション記法の誤り等）を含むファイルを、既定では例外として扱う。アプリでは次のとおりとする。

- `ThrowOnError = false`で読み込み、エラーがあっても内容を表示する。エラーは診断情報一覧に表示し、メッセージでも通知する
- エラーの行は読み込まれていない（ライブラリの仕様で無視される）ため、そのまま保存すると元のファイルからその行が失われる。エラーを含むファイルを保存する場合は、その旨を表示して確認する
- 診断情報は読み込み時点のものとし、編集しても更新しない（ライブラリの仕様と同じ）

### 4-4. 元に戻す（Undo）

- 対象は、文書を変更する操作（値の変更、キーの追加・削除、セクションの追加・削除）とする
- 元に戻すと、その操作の前の状態（キー・セクションの位置、付いていたコメントを含む）に戻る
- 複数回さかのぼれる。さかのぼれる回数の上限は次工程で決める
- ファイルを開く・新規作成を行うと、元に戻せる履歴は消える。保存しても履歴は消えない
- 元に戻した操作をもう一度行う機能（やり直し：Redo）は設けない（6章）

### 4-5. コメントの確認（保存イメージ）

LFCファイルのコメントには設定の説明が書かれていることが多く、値を編集する際に確認できた方がよい。一方、ライブラリにはコメントを取得・設定する公開APIがない。そのため、次の案から、ライブラリを変更せずに実現できる案Aを採用する。

| 案 | 内容 | ライブラリの変更 | 結論 |
|---|---|---|---|
| A | 保存したときのテキスト（`ToText()`の結果）を、保存イメージとして読み取り専用で表示する | 不要 | **採用** |
| B | キー一覧にコメントの列を設け、キーごとに前置コメント・行末コメントを表示する | 必要（コメントを取得する公開APIの追加） | 不採用（必要になった場合は別途相談する） |
| C | Bに加え、コメントを編集できるようにする | 必要（コメントを取得・設定する公開APIの追加） | 不採用 |

- 保存イメージには、コメントが付いている要素とあわせて、保存時のテキストをそのまま表示する
- 編集するたびに表示を更新する。保存前に、保存される内容の確認にも使える
- 保存イメージ上で編集することはできない

## 5. 非機能要件

| No | 要件 |
|----|------|
| 1 | 開発言語：C#（.NET 8）、UIフレームワーク：WPF。動作環境はWindows 10／11 |
| 2 | 画面（View）と処理を分離する（MVVMパターン）。画面の処理はViewModelに置き、コードビハインドには画面固有の処理だけを書く |
| 3 | ViewModelのロジックは、画面を表示せずにユニットテストで検証できる構成とする（ファイルダイアログ・メッセージボックスはインターフェイス経由で呼び出す） |
| 4 | LFCの読み書き・型判定はアプリで実装せず、`FileParserLib`に任せる |
| 5 | 外部ライブラリは、`FileParserLib`とテスト用ライブラリ（xUnit）以外は使わない（MVVMの基盤も標準機能で実装する） |
| 6 | ファイルの読み書き中に例外が発生しても、アプリを異常終了させない |
| 7 | コーディング規約・フォルダ構成・修飾子の方針は、`FileParserLib`と同じとする（1ファイル1クラス、フォルダと名前空間の一致など） |

## 6. スコープ外（今回は扱わない事項）

- キー名・セクション名の変更（ライブラリに名前を変更するAPIがなく、削除と追加で代用すると位置やコメントが変わるため）
- キー・セクションの並べ替え（ライブラリに並べ替えのAPIがないため）
- キーごとのコメントの表示、コメントの編集（ライブラリにコメントを取得・設定する公開APIがないため。コメントは保存イメージで確認する（4-5））
- やり直し（Redo）。元に戻す（Undo）だけを設ける（4-4）
- 複数ファイルの同時編集、タブ表示
- 検索・置換
- LFCファイル以外の形式（INI、CSV等）の読み書き
- ライブラリ（`FileParserLib`）の仕様変更。必要が生じた場合は別途相談する

## 7. 次工程（基本設計）で検討する事項

- 画面レイアウトの詳細（各領域の配置、コントロールの種類：`ListBox`／`TreeView`、`DataGrid`等）と画面遷移
- 保存イメージの配置（常に表示するか、切り替えて表示するか）と、キーを選択したときに保存イメージの該当行へ移動するか
- ViewModelの構成（メイン画面、セクション、キー行など）と、`LfcDocument`との対応
- コマンド（`ICommand`）と、実行できる条件（例：ファイルを開いていないときは保存できない）
- 入力した値の表記を`LfcValue`の一覧に変換する方法。ライブラリの型判定のクラスは非公開（`internal`）のため、公開APIだけで実現できるか（例：`LfcDocument.Parse`の利用）と、できない場合のライブラリへのAPI追加の要否
- 元に戻す（Undo）の実現方法。ライブラリには文書を複製するAPIがなく、削除したキーを`Set`で戻すと末尾に追加されコメントも失われるため、操作前の状態の保存方法（例：`ToText`の結果を保存し、`Parse`で戻す）を検討する。あわせて、履歴の上限と、元に戻した結果が保存時と同じになった場合に「変更あり」を解除するか
- 保存していない変更の判定方法（編集したら「変更あり」とする／保存した内容と比較する）
- エラーメッセージの文言と表示方法（メッセージボックス、診断情報一覧への追記など）
- ファイルダイアログ・メッセージボックスを抽象化するインターフェイスの設計
- `FileParserLib`の参照方法（DLLを配置する／Gitのサブモジュールにする等）
