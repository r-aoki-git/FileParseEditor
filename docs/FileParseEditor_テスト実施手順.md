# FileParseEditor テスト実施手順

テスト仕様書（`docs/FileParseEditor_テスト仕様書.xlsx`）のテストを実施し、検証ログ（`docs/FileParseEditor_検証ログ.md`）を仕上げて、最終レビューに提出するまでの手順。スケジュールの No.12（テストの実施、不具合の修正、検証ログ）と No.13（最終レビュー）にあたる。

上から順に進めれば終わるように書いている。迷ったら「7. よくある質問」を見る。

## 0. 全体の流れと時間の目安

| 順 | 作業 | 目安 | 成果物 |
|---|---|---|---|
| 1 | 準備（最新のソースの取得、ビルド、作業用フォルダ、キャプチャの準備） | 30分 | ― |
| 2 | 単体テストの実施（スクリプトを実行するだけ） | 10分 | 検証ログ 5章 |
| 3 | 機能テスト（F-01〜F-24）の実施 | 2〜3時間 | テスト仕様書、`docs/エビデンス/` |
| 4 | エラーケーステスト（E-01〜E-11）の実施 | 1〜1.5時間 | 同上 |
| 5 | 検証ログの記入 | 30分 | 検証ログ |
| 6 | 提出（コミット、プルリクエスト）と最終レビュー | 30分＋レビュー | プルリクエスト |

NG が出た場合は「4. NG が出たとき」の手順で直してから、そのテストだけやり直す。

## 1. 準備

### 1-1. 最新のソースを取得する

テストは、全ての機能が入った `main` ブランチで行う。

```
cd （FileParseEditor のフォルダ）
git checkout main
git pull
```

Visual Studio を使う場合は、メニューの「Git」→「プル」でもよい。取得できたら、`docs` フォルダに `FileParseEditor_テスト実施手順.md`（このファイル）と `FileParseEditor_検証ログ.md` があることを確認する。

### 1-2. ビルドして起動を確認する

1. Visual Studio で `FileParseEditor.sln` を開く
2. ソリューション エクスプローラーで `FileParseEditor`（`.Core` や `.Tests` ではない）を右クリックし、「スタートアップ プロジェクトに設定」を選ぶ
3. メニューの「ビルド」→「ソリューションのビルド」（Ctrl+Shift+B）で、エラーがないことを確認する
4. F5（デバッグ開始）または Ctrl+F5（デバッグなしで開始）で起動し、タイトルが「FileParseEditor - 無題」の画面が出ることを確認して閉じる

### 1-3. 作業用のフォルダを作る

保存のテストでファイルが書き換わるため、`testdata` のファイルは直接使わず、コピーして使う。

1. 例えば `C:\work\FileParseEditorTest` のようなフォルダを作る（リポジトリの外に作る）
2. リポジトリの `testdata` フォルダから、`normal.lfc`・`warnings.lfc`・`errors.lfc` をコピーする
3. ファイルを書き換えるテスト（F-17〜F-23、E-02〜E-05）の前に、元の内容に戻したい場合は、もう一度コピーし直す（上書きでよい）

### 1-4. 大きなファイルを作る（F-24 用）

PowerShell を開き、作業用のフォルダで次を実行する（数秒で終わる）。

```
cd C:\work\FileParseEditorTest
$l = @("[Big]") + (1..200000 | % { "Key$_ = $_" }); Set-Content large.lfc $l -Encoding Ascii
```

`large.lfc`（約4MB）ができればよい。

### 1-5. キャプチャの取り方と保存先

- Windows の「Win + Shift + S」で範囲を選び、右下に出る通知をクリックして「切り取り＆スケッチ」（または Snipping Tool）で保存する
- 保存先はリポジトリの `docs/エビデンス/`、ファイル名はテストIDにする（例：`F-01.png`）。テスト仕様書のエビデンス欄にも同じ名前が書いてある
- 1つのテストで何枚か撮りたい場合は `F-16_1.png`、`F-16_2.png` のように番号を付け、テスト仕様書のエビデンス欄を書き換える
- 撮るのは「確認項目が確認できる画面」でよい（メッセージが出るテストは、メッセージが出ている画面）

### 1-6. テスト仕様書の記入のしかた

テスト仕様書は Excel で開き、テストを1つ終えるごとに、そのテストの「手順」の1行目に記入する。

| 列 | 記入する内容 |
|---|---|
| 確認日付 | テストを行った日付（例：2026/11/25） |
| 判定 | 確認項目を全て満たしたら「済」、1つでも満たさなければ「NG」 |
| エビデンス | 確認項目の1行目に、保存したキャプチャのファイル名が書いてある。名前を変えた場合だけ書き換える |
| 備考 | NG の場合は、どの確認項目がどうだったかを書く。補足があれば書く（例：「ファイルの読み込みが速く、読み込み中の表示は一瞬だった」） |

## 2. 単体テストの実施

PowerShell をリポジトリのフォルダで開き、次を実行する。

```
powershell -ExecutionPolicy Bypass -File scripts\Run-UnitTests.ps1 -Executor "青木蓮"
```

- 全ての単体テスト（284件）をカバレッジ付きで実行し、`docs/FileParseEditor_検証ログ.md` の「5. 単体テストの結果」を自動で書き換える（他の章は変えない）
- 最後に「結果: 284 件中 284 件成功、0 件失敗」と出れば成功。検証ログの5章に、実行日時・実行環境・件数・カバレッジ・テストクラスごとの件数が書き込まれていることを確認する
- 終わったら、テスト仕様書の「単体テスト」シートの全ての項目に、確認日付と「済」を記入する（エビデンスは「dotnet test の結果」のままでよい。中身は検証ログの5章）
- 失敗したテストがある場合は、黄色の警告が出て、検証ログの5章に失敗したテストの一覧が書き込まれる。「4. NG が出たとき」へ進む

Visual Studio のテスト エクスプローラー（「テスト」→「テスト エクスプローラー」→「すべてのテストを実行」）でも実行できるが、検証ログは書き換わらないため、提出用にはスクリプトを使う。

## 3. 機能テスト・エラーケーステストの実施

### 3-1. 進め方

1. テスト仕様書の「機能テスト」シートを開き、F-01 から順に進める
2. 「手順」のとおりに操作し、「確認項目」を全て確認する
3. キャプチャを `docs/エビデンス/` に保存する
4. テスト仕様書に確認日付と判定を記入する（1-6）
5. 「機能テスト」が終わったら、「エラーケーステスト」シートを E-01 から同じように進める

各テストは、特に書いていなければ、アプリを起動し直さずに続けて行ってよい。前のテストで文書を編集していて、ファイルを開くときに「変更を保存しますか？」と聞かれた場合は、「いいえ」を選べばよい（F-21〜F-23 は、この確認そのものを確かめるテスト）。

### 3-2. テストごとの注意点

手順に書いてあるとおりに操作すればよいが、迷いやすい点を挙げる。

| ID | 注意点 |
|---|---|
| F-01 | 起動した直後の画面で確認する。「編集」メニューを開いて、項目が灰色になっていることを確認する |
| F-02 | ファイルを開くダイアログの右下（ファイルの種類）が「LFCファイル (*.lfc)」になっていることを確認する |
| F-03 | エクスプローラーからファイルをドラッグし、アプリの画面の上で離す。1回目はキー一覧の上、2回目は右側の保存イメージの上で離す |
| F-04 | Lines の値は `"1行目\n2行目\tタブ"` のように、`\n`・`\t` がそのまま文字で表示されるのが正しい（保存時と同じ表記） |
| F-08〜F-10 | 値の編集欄は、キー一覧の下にある。Enter キーまたは「確定」ボタンで確定する |
| F-13 | Delete キーは、キー一覧をクリックしてから押す（値の編集欄にカーソルがあると、文字の削除になる） |
| F-16 | 「元に戻す」は、編集メニューから選ぶか、キー一覧をクリックしてから Ctrl+Z を押す。確認項目 4 は、値の編集欄に何か入力した状態で Ctrl+Z を押し、入力欄の文字が戻ることを確認する |
| F-17 | メモ帳（Windows 11）では、画面の一番下の右側に「UTF-8」と「Unix (LF)」が表示される。表示されていない場合は、メモ帳の「表示」→「ステータス バー」をオンにする。「UTF-8 (BOM 付き)」と表示されたら NG |
| F-19 | ファイル名に既にある `warnings.lfc` を選んで「保存」を押すと、Windows の「上書きしますか？」の確認が出る。テストの後、`warnings.lfc` を `testdata` からコピーし直す |
| F-21 | 手順 4 で「はい」を押すと、normal.lfc が保存されてからファイルを開くダイアログが出る。ダイアログはキャンセルしてよい。テストの後、`normal.lfc` をコピーし直す |
| F-23 | 手順 2 の「いいえ」でアプリが終了するので、手順 3 では起動し直す。最後の確認項目 5 は、起動直後（変更なし）に閉じるボタンを押して確認する |
| F-24 | 1-4 で作った `large.lfc` を使う。読み込みが速くて「読み込み中」の表示が見えない場合は、1-4 の `200000` を `1000000` に変えて作り直す。それでも一瞬で終わる場合は、備考に「読み込みが速く、読み込み中の表示は一瞬だった」と書き、画面が固まらなかったことを確認できれば「済」でよい |
| E-01 | メッセージは「OK」で閉じてから、診断情報の一覧と、セクションごとのキーを確認する |
| E-02 | 作業用の `errors.lfc` を使う（ファイルが書き換わる）。テストの後、`errors.lfc` をコピーし直す |
| E-04 | ファイルを右クリック →「プロパティ」→「セキュリティ」タブ →「編集」→ 自分のユーザーを選び、「読み取り」の「拒否」にチェックを付けて「OK」。テストの後、同じ画面でチェックを外す。会社のパソコンの設定でアクセス権を変えられない場合は、判定を空欄のまま、備考に「アクセス権を変更できず実施できなかった（読み込みに失敗したときの M11 の表示と、文書が変わらないことは、単体テストの MainViewModelOpenTests で確認済み）」と書く |
| E-05 | ファイルを右クリック →「プロパティ」→「全般」タブの下にある「読み取り専用」にチェックを付けて「OK」。テストの後、チェックを外す |
| E-08 | 値の編集欄は1行の入力欄のため、2行の文字を貼り付けると、改行が入らずに1行目だけ（または改行を除いた文字）が入ることがある。その場合も、改行を含む値が設定されなければ「済」でよい。どうなったかを備考に書く |
| E-10・E-11 | メッセージを閉じると、同じダイアログが入力した内容のまま再表示されることを確認する。確認が終わったらダイアログは「キャンセル」で閉じる |

## 4. NG が出たとき

1. テスト仕様書の判定に「NG」、備考にどの確認項目がどうだったかを書く
2. 検証ログの「6. 不具合と対応」に1行追加する（No、テストID、内容。原因・対応・再テストは後で書く）
3. キャプチャ（NG の画面）を保存する
4. 修正を依頼する。Claude に依頼する場合は、次をそのまま伝えればよい
   - テストID（例：F-16）
   - 行った手順
   - 期待した結果（テスト仕様書の確認項目）と、実際の結果
   - 可能ならキャプチャ
5. 修正が `main` に入ったら、`git pull` してビルドし直し、NG だったテストだけをやり直す（2 の単体テストも、もう一度スクリプトを実行する）
6. やり直して確認できたら、テスト仕様書の確認日付・判定（「済」）を書き換え、備考に「（日付）再テストで OK」と書く。検証ログの6章の原因・対応・再テストも記入する

明らかに手順の書き間違い（テスト仕様書の誤り）だった場合は、アプリは直さず、テスト仕様書の手順・確認項目を直して、備考に「手順を修正」と書く。

## 5. 検証ログの記入

`docs/FileParseEditor_検証ログ.md` を開き、「（記入）」の箇所を書き換える。

| 章 | 記入する内容 |
|---|---|
| 1. 概要 | 対象（`git log --oneline -1` の先頭7文字）、実施日、実施者、実行環境（Windows のバージョンは「設定」→「システム」→「バージョン情報」、Visual Studio のバージョンは「ヘルプ」→「Microsoft Visual Studio のバージョン情報」）、結果 |
| 3・4. 結果 | 各テストの判定（OK／NG）。エビデンスのファイル名を変えた場合は書き換える。備考は、テスト仕様書の備考と同じ内容でよい |
| 5. 単体テストの結果 | 書かなくてよい（スクリプトが書き込む） |
| 6. 不具合と対応 | NG がなければ、表の1行目に「なし」と書く |
| 8. まとめ | 全て OK なら、例の文章のとおりでよい。残課題がなければ「なし」 |

## 6. 提出と最終レビュー

### 6-1. コミットとプルリクエスト

テスト仕様書・検証ログ・エビデンスをコミットし、プルリクエストを作る。

```
git checkout -b test-results
git add docs/FileParseEditor_テスト仕様書.xlsx docs/FileParseEditor_検証ログ.md docs/エビデンス
git commit -m "テストの実施結果（テスト仕様書・検証ログ・エビデンス）を追加"
git push -u origin test-results
```

GitHub でプルリクエストを作り、`main` にマージする。Claude に「テスト結果のプルリクエストを作って」と依頼してもよい。

### 6-2. 提出するもの

| 種類 | ファイル |
|---|---|
| ドキュメント | `docs/FileParseEditor_要件定義書.md`、`docs/FileParseEditor_基本設計書.md`、`docs/FileParseEditor_スケジュール.md`、`docs/FileParseEditor_テスト仕様書.xlsx`、`docs/FileParseEditor_検証ログ.md`、`docs/エビデンス/` |
| 図 | `diagrams/`（作図用 PlantUML）と、それを元に作成した astah の図 |
| ソースコード | `FileParseEditor.sln`、`FileParseEditor/`、`FileParseEditor.Core/`、`FileParseEditor.Tests/`、`lib/`、`scripts/`、`testdata/`、`README.md`、`.editorconfig`、`.gitattributes` |
| 提出しないもの | `bin/`・`obj/`・`.vs/` フォルダ（ビルドすると作られる。`.gitignore` で除外済み） |

GitHub のリポジトリ（`main` ブランチ）を見てもらう形で提出する場合は、6-1 のプルリクエストをマージすれば、上の全てが揃っている。

### 6-3. 提出前の確認

- [ ] 要件定義書の「4. 要求確認事項」で「要確認」のままの項目（画面構成）を、レビューで確認できていれば「決定」に書き換えた
- [ ] テスト仕様書の全ての項目に、確認日付と判定が記入されている
- [ ] 検証ログに「（記入）」が残っていない
- [ ] `docs/エビデンス/` に、テスト仕様書のエビデンス欄に書いた全てのファイルがある
- [ ] 単体テストのスクリプトを、提出するコミットで最後に実行した（検証ログ5章の「対象コミット」が、提出するコミットと同じ）

### 6-4. 最終レビューで指摘を受けたら

指摘の内容を Claude に伝えれば、ソースコード・設計書・テスト仕様書を直してプルリクエストを作る。直した後は、影響のあるテストだけをやり直し、4 の 5〜6 と同じように記録する。

## 7. よくある質問

| 質問 | 答え |
|---|---|
| 起動すると「スタートアップ プロジェクトが…」と出て起動しない | 1-2 の 2 で、`FileParseEditor` をスタートアップ プロジェクトにする |
| スクリプトを実行すると「このシステムではスクリプトの実行が無効になっている」と出る | コマンドの先頭の `powershell -ExecutionPolicy Bypass -File` を付けて実行する（2 のコマンドをそのまま使う） |
| スクリプトの日本語が文字化けする | スクリプトを Visual Studio などで開いて保存し直すと、文字コードが変わることがある。`git checkout -- scripts/Run-UnitTests.ps1` で元に戻す |
| テストの途中で、前のテストの編集が残っている | 「新規作成」で空の文書に戻すか、アプリを起動し直す。保存の確認が出たら「いいえ」 |
| 保存したら testdata のファイルが変わってしまった | `git checkout -- testdata` で元に戻せる。次からは作業用のフォルダ（1-3）のファイルを使う |
| 判定に迷う（確認項目どおりではないが、問題とも言い切れない） | 「NG」にして備考に状況を書き、修正するかを相談する。テスト仕様書の書き方の問題であれば、4 の最後の段落のとおりに直す |
| エビデンスは全ての確認項目について必要か | 1つのテストにつき、確認項目が分かる画面を1枚以上でよい（1-5） |
